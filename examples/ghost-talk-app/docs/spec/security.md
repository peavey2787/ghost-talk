# Security invariants

- No plaintext mnemonic/private key at rest or in logs.
- One 24-word BIP39 seed is the recovery root for both subsystems; HYDRA receives only a 32-byte BLAKE3 derive-key output under the `GhostTalk/HYDRA-ID/v1` domain, never a Kaspa BIP32 private key.
- UI cannot grant cryptographic authorization.
- Manual wallet + mailbox unlock is the default for each app session. Once unlocked, the password stays only in process memory and can authorize KAS sends unless the user enables per-send password re-entry.
- Disabling the session unlock prompt is an explicit device-trust mode: changing the policy requires the current wallet password, and an authenticated AES-GCM-protected unlock-equivalent credential is stored separately from profile JSON in app-local storage. The UI warns that local application-data compromise can then open both wallet and messaging identity.
- Audience cannot create traffic accepted as Presenter.
- Blocked contacts are rejected before application delivery.
- Bound every untrusted length/count; reject conflicting fragments.
- Replay/duplicate delivery is idempotent.
- Durable checkpoint never advances past uncommitted carrier/event state.
- KNS mapping changes are visible; GTCD is address-signature verified by the full integration build.
- DotK directory/index data is never accepted as ownership proof. The index supplies only candidate `ownerType + owner`; directory-supplied payment/deed addresses, scripts, and registry metadata are ignored. Mainnet `.k` resolution pins the registry/deed deployment, derives the deed locally, verifies the exact bond/script and registry `covenant_id` directly through the active wRPC endpoint via Kaspa Portal, and rechecks that the same outpoint is still live before returning a recipient address.
- Kaspa-only voice spending is explicit and bounded.
- Only `ghost-hydra` imports HYDRA; only `ghost-kaspa` imports Portal; Kinesis has no runtime edge.
- Encryption is mandatory; steganography and routing privacy are independent optional properties.
- Live HYDRA ratchet state is deliberately not persisted. Restart recovery establishes a new authenticated session from the already verified GTCD peer binding; stale ciphertext stays queued until that recovery succeeds.
- Delivery receipts are not trusted merely because they appear on Kaspa: GTAK receipts are domain-separated and BIP340-verified against the peer's previously verified stable Kaspa P2PK route, and bind signer HYDRA id, destination HYDRA id and logical message id.
- Native profile metadata has one authoritative Ghost Talk data root with serialized writes and a synced temp/previous-snapshot commit sequence. Every supported platform resolves that root through Tauri's application-data API, keeping OS-specific storage conventions behind one abstraction rather than writing beside the executable. Release builds use that root directly; debug/development builds use its `development/` child so a development instance can run beside a release instance without sharing mutable HYDRA/profile state. Ghost Talk owns same-profile exclusion with a cross-platform OS advisory lease held for the complete HYDRA facade lifetime. The lease is released automatically by the OS on normal exit or crash, so a leftover lease file is never treated as ownership. The pinned HYDRA crate still writes a PID-only compatibility sentinel; Ghost Talk checks process start time against that sentinel's write time so a recycled live PID cannot permanently strand a profile. If the stale sentinel happens to contain the newly launched Ghost Talk process's recycled numeric PID, the already-held per-profile lease proves that this process has no second live facade for that directory, so the compatibility sentinel is reaped instead of falsely self-locking. Ghost Talk removes only a proven-stale upstream sentinel and retries HYDRA open once.
- New direct sessions use Ghost Talk KKTP v2 with a high-entropy session `sid`, immutable Initiator/Responder role ordering, a domain-separated SHA3-256 mailbox ID, and independent monotonic receive/send sequence state per direction.
- KKTP outer routing/order fields are duplicated inside the HYDRA-encrypted canonical plaintext and MUST match after authenticated decryption before application delivery.
- The reference KKTP classical X25519/Ed25519/static-XChaCha profile is not Ghost Talk's session-security profile: HYDRA remains authoritative with ML-DSA-65 identity authentication, hybrid X25519 + ML-KEM-768 establishment, HKDF-HMAC-SHA3-256, and ratcheted ChaCha20-Poly1305 one-use message keys.
- Kaspa BIP340 signatures on KKTP Discovery/Response prove routing-address control; they do not replace HYDRA's post-quantum identity authentication.
- Every KKTP `ghost_handshake` (`pq_init`, `pq_resp`, `pq_finish`) is additionally signed as canonical context with the sender's HYDRA ML-DSA-65 identity key before the receiver may act on its SID, roles, stage, HYDRA payload, or optional first-message metadata.
- Retired KKTP SIDs are process-locally replay-blocked with a bounded 4096-entry cache; durable mailbox transaction-ID deduplication is the persistent replay boundary.
- Reprocessing the exact same accepted Discovery/Response SID is idempotent and MUST NOT tear down or rewind an already progressing/active ratchet.
- Leaving a pending conversation uses HYDRA's explicit per-contact handshake abort rather than calling `close_session` on a session that does not yet exist. New conversations with the same peer require a new `sid`; archive never changes this state implicitly.
- Leaving an active conversation emits a canonical KKTP v2 `session_end` anchor dual-authenticated by the sender: ML-DSA-65 binds the HYDRA/PQ identity and Kaspa BIP340 binds the routing key and the included PQ signature. A receiver changes state only after both signatures, the participant tuple, destination route, and exact SID verify.
- A verified `session_end` closes and retires only its exact current SID, blocks native sends for that ended peer session, and makes the matching persisted chat read-only. A delayed close for an older SID MUST NOT close a newer chat; explicit Start chat/rejoin clears the peer block only while creating a fresh SID. After process restart, when no volatile binding exists, a valid close may mark only the persisted matching SID ended; it MUST NOT create an unscoped peer-global block that could poison a newer SID.
- Incoming KKTP v2 security records MUST be canonical JSON on the wire; parse-and-reencode mismatches are rejected.
- Authenticated application plaintext is routed only to the exact persisted active `sid` for that peer. Historical Discovery/Response/message/session-end carriers from another SID cannot replace or populate a newer conversation. After volatile-ratchet loss, a fresh recovery SID becomes persisted authority only after its signed recovery `pq_init` carrier has been accepted by Kaspa.
- Active-session KKTP send preparation is transactional with respect to protocol state: the exact `sid`/`seq`/HYDRA ciphertext is cached by logical `message_id` and reused while Kaspa submission is unresolved, then evicted when every required physical carrier is accepted. A retry after a failed or ambiguous submission must never consume a second ratchet step or sequence number for the same logical message. Ordinary active messages have no second receipt transaction; the signed ACK retained for `pq_finish` is bootstrap/session-activation evidence only. The volatile cache is bounded to 4096 unresolved entries and is cleared on session teardown.
- A post-encryption framing/size failure cannot be rolled back inside HYDRA. Ghost Talk therefore closes/retires that volatile session immediately instead of continuing after a consumed but unpublished KKTP sequence; the next send must establish a fresh SID.
