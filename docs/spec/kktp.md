# Ghost Talk KKTP v2 — HYDRA-PQ profile

Ghost Talk uses a deployment profile of the **Kaspa Kinesis Transport Protocol (KKTP)** for direct-chat discovery, consent, session identity, mailbox addressing, ordering, replay handling, and session lifecycle. The transport profile is versioned as **Ghost Talk KKTP v2**.

The upstream/reference KKTP document describes classical X25519/Ed25519 key agreement and a single static XChaCha20-Poly1305 session key. Ghost Talk **does not use those classical session-security primitives**. KKTP is the Kaspa transport/state-machine layer; **HYDRA-MSG is the cryptographic authority**.

## Cryptographic profile

Ghost Talk's direct-session cryptography remains HYDRA-MSG's pinned authenticated hybrid-PQ protocol:

- identity authentication: **ML-DSA-65**;
- ephemeral key establishment: **X25519 + ML-KEM-768**;
- KDF: **HKDF-HMAC-SHA3-256**;
- transcript hashing: **SHA3-256 / SHA3-512** as specified by HYDRA;
- message protection: HYDRA's ratcheted **ChaCha20-Poly1305** channel with one-use message keys;
- authenticated three-stage establishment: HYDRA `INIT`, `RESP`, and `FINISH`.

The reference KKTP requirement for a random 192-bit XChaCha nonce is therefore **replaced by HYDRA's ratchet nonce/key schedule**. HYDRA derives a one-use AEAD key per protected record; its protocol fixes the ChaCha20-Poly1305 nonce to the HYDRA-defined value only because no AEAD key is reused for a different plaintext. Ghost Talk never invents or overrides HYDRA nonces.

Kaspa BIP340 signatures on Discovery/Response records prove control of the Kaspa routing address. They are **not** treated as the post-quantum identity primitive. The embedded HYDRA contact card and the subsequent ML-DSA-authenticated HYDRA transcript bind the actual messaging identity.

## Session roles and `sid`

A direct session has exactly two immutable roles for one `sid`:

- **A / Initiator** — the peer that publishes the Discovery anchor;
- **B / Responder** — the peer that accepts it and publishes the Response anchor.

`sid` is a random 128-bit lowercase hexadecimal value generated by Ghost Talk. This is equivalent in entropy class to the UUID-v4 example permitted by the KKTP reference. A new direct conversation with the same person receives a new `sid`; archived conversations keep their old `sid` and are never implicitly reopened.

A fresh recovery handshake after volatile ratchet loss also receives a fresh `sid`. Old-session ciphertext can never be admitted into that replacement session.

## Discovery and consent anchors

Logical anchor records use the canonical prefix:

```text
KKTP:ANCHOR:<canonical-json>
```

Ghost Talk defines two consent anchors:

```json
{
  "type": "discovery",
  "version": 2,
  "sid": "<128-bit hex>",
  "recipient_kaspa_address": "<exact destination>",
  "sender": "<signed Ghost Contact Descriptor>",
  "sig": "<Kaspa BIP340 signature>"
}
```

```json
{
  "type": "response",
  "version": 2,
  "sid": "<same sid>",
  "recipient_kaspa_address": "<initiator return address>",
  "acceptor_kaspa_address": "<exact address that received discovery>",
  "responder": "<signed Ghost Contact Descriptor>",
  "sig": "<Kaspa BIP340 signature>"
}
```

The exact contacted address is signed so acceptance cannot be detached from the destination the initiator actually selected. The responder's HYDRA contact card is not persisted as an accepted contact until the user explicitly presses **Accept**.

All security-relevant KKTP JSON emitted by Ghost Talk is canonicalized before signing/encoding. Incoming v2 records are parsed, reconstructed canonically, and rejected if their wire bytes are not the canonical encoding. Ghost Talk's current schemas contain only strings, booleans, integer counters, arrays, objects, and null/optional fields; no floating-point security field is permitted.

## PQ handshake extension

HYDRA cannot safely derive its session solely from the public KKTP Discovery/Response objects because its authenticated hybrid-PQ handshake has its own transcript, fresh X25519 material, ML-KEM material, ML-DSA signatures, confirmation values, and FINISH step. Ghost Talk therefore defines a versioned KKTP anchor extension:

```json
{
  "type": "ghost_handshake",
  "version": 2,
  "sid": "<sid>",
  "stage": "pq_init|pq_resp|pq_finish",
  "initiator_hydra_id": "<A identity fingerprint>",
  "responder_hydra_id": "<B identity fingerprint>",
  "payload_b64": "<opaque HYDRA INIT/RESP/FINISH>",
  "first_message": null,
  "pq_sig_b64": "<ML-DSA-65 signature>"
}
```

`pq_sig_b64` is mandatory. The sender signs the canonical handshake-control object with `pq_sig_b64` omitted using the active HYDRA ML-DSA-65 identity key. Ghost Talk domain-separates that signature as:

```text
SHA3-512(
    "HYDRA-MSG/GhostTalk/KKTP/v2/context\0" ||
    u64_be(canonical_context_length) ||
    canonical_context
)
```

The receiving peer verifies the signature against the already authenticated HYDRA contact key **before** acting on `sid`, role, stage, the opaque HYDRA handshake bytes, or the optional first-message metadata. This makes the KKTP wrapper itself post-quantum identity-authenticated instead of relying only on the signatures internal to the opaque HYDRA transcript. Kaspa BIP340 still proves routing-address ownership for Discovery/Response; it is not substituted for this ML-DSA identity binding.

The role order is fixed by the Discovery/Response exchange, never by lexical address order and never by whichever peer happens to process a block first.

Normal first-contact flow is:

```text
A                                  Kaspa                                  B
|                                                                           |
|-- Discovery(sid, A descriptor) ------------------------------------------>|
|                                                           user Accepts     |
|<-------------------------------- Response(sid, B descriptor) -------------|
|                                                                           |
|-- pq_init(sid, HYDRA INIT) ---------------------------------------------->|
|<-------------------------------- pq_resp(sid, HYDRA RESP) ----------------|
|-- pq_finish(sid, HYDRA FINISH + optional encrypted first message) ------->|
|                                                                           |
|=========================== ACTIVE ========================================|
```

Only A initiates this initial PQ handshake. Messages typed by B while establishment is pending stay locally queued until authenticated `pq_finish` activates the session. This prevents a second application-level handshake race on top of HYDRA's own collision rules.

## Mailbox ID

Ghost Talk derives a 32-byte mailbox identifier using SHA3-256 with explicit domain separation:

```text
mailbox_id = SHA3-256(
    "GhostTalk/KKTP/v2/mailbox\0" ||
    initiator_hydra_id_bytes ||
    responder_hydra_id_bytes ||
    sid_bytes
)
```

A is always encoded first. Reversing roles, changing either identity, or changing `sid` yields a different mailbox.

Retired SIDs are also kept in a bounded in-memory replay cache (maximum 4096 entries). Durable Kaspa transaction-ID deduplication remains the primary replay boundary across scanning/restarts; the SID cache is a fast process-local guard and is intentionally bounded against untrusted long-lived growth.

## Encrypted messages

After activation, a logical on-chain packet is:

```text
KKTP:<mailbox_id>:<canonical-json>
```

with an outer record containing:

```json
{
  "type": "msg",
  "version": 2,
  "sid": "<sid>",
  "mailbox_id": "<hex>",
  "direction": "AtoB|BtoA",
  "seq": 0,
  "sender_hydra_id": "<hex>",
  "message_id": "<128-bit hex>",
  "profile": "<HYDRA stego profile>",
  "ciphertext_b64": "<HYDRA envelope>"
}
```

Before HYDRA encryption, Ghost Talk creates an inner canonical record containing the same `sid`, `mailbox_id`, direction, sequence, and logical message ID plus the plaintext body. The receiver accepts application plaintext only if:

1. the outer `sid`, mailbox, sender and direction match the active native session binding;
2. `seq` is exactly the next expected sequence for that direction;
3. HYDRA authenticates/decrypts the envelope;
4. the authenticated inner metadata exactly matches the outer metadata.

This makes the KKTP routing/order fields cryptographically bound even though HYDRA owns the AEAD AAD format internally.

## Ordering, replay, and BlockDAG reassembly

Each direction begins at sequence `0` and advances independently.

- `seq < expected`: replay/duplicate; discard without application delivery.
- `seq == expected`: authenticate, validate inner/outer binding, deliver, then advance.
- `seq > expected`: retain the durable carrier and wait for the gap rather than delivering out of order.
- a packet from an old `sid` is stale and can never become valid in a replacement session.

Ghost Talk retains stable random `message_id` values for deduplication and exact failed-submit retry. Ordinary **active-session** messages retain one logical KKTP carrier per message. Ghost Talk may split that carrier into multiple GHST physical Kaspa transactions so no KSPT-v1 payload exceeds 65,535 bytes; the message becomes **Delivered** after every required physical fragment has been accepted by Kaspa. This status means the durable carrier was successfully broadcast to the Kaspa network. Ghost Talk does not emit a second per-message receipt transaction. Signed Kaspa acknowledgements remain only for the special `pq_finish` bootstrap/session-activation proof described below.

Application routing is SID-strict. After canonical outer/inner authentication, the verified `sid` is preserved with the decrypted projection and the UI may append it only to the exact non-ended thread carrying that SID. Historical same-peer Discovery/Response traffic cannot overwrite a newer active thread SID. If a restart loses the volatile ratchet and native recovery creates a replacement SID, the UI persists that replacement only after the recovery `pq_init` carrier is accepted by Kaspa, so subsequent mailbox drains and restarts agree on the one authorized SID.

### Bootstrap liveness and serialized local consumption

Kaspa is the durable mailbox, but live detection does not wait for an address-history index. Ghost Talk’s single Kaspa Portal connection subscribes to `BlockAdded`; each notification carries the full block, and the native scanner inspects that block’s transaction payloads directly for `KKTP:`/Ghost carriers. The live path does not issue REST `GetBlocks`, does not require UTXO-change notifications, does not depend on optional output-address metadata, and has no polling/debounce interval between a received block notification and carrier processing. REST/indexer history is archival-only: it may return carriers only when their block timestamp proves they are older than 48 hours, and it runs separately so archival latency cannot stall live notification handling. Recent/current carrier truth comes from Kaspa Portal wRPC, not REST. After a bootstrap carrier has been successfully submitted, Ghost Talk does **not** republish Discovery, Response, `pq_init`, or `pq_finish` on a success timer. The UI still serializes already-observed envelope application so an older async event cannot overtake newer state; this local drain does not define the network polling cadence. Exact-SID duplicate Discovery/Response records remain idempotent for compatibility with older revisions and transaction-history replay, and wallet-authored loopback traffic is authenticated then discarded.

For an active session, preparing a message advances both HYDRA's sending ratchet and the KKTP directional sequence. Ghost Talk therefore keeps the **exact prepared logical packet** (`sid`, `seq`, HYDRA ciphertext, and outer canonical record) in volatile native memory under that `message_id` while its Kaspa submission is unresolved. An explicit retry after an actual or ambiguous submission failure reuses those exact bytes; it MUST NOT call HYDRA encryption again or allocate a new KKTP sequence number. A successful `SubmitTransaction` commits an ordinary active-session packet locally and releases this retry entry; no second signed receipt transaction is created. This prevents a failed or ambiguously observed carrier for `seq = n` from being regenerated as `seq = n + 1` and permanently blocking the receiver's strict reassembly window. The cache is bounded to 4096 unresolved messages and is erased with the volatile session state on Leave/lock/restart.

The special first plaintext optionally carried inside `pq_finish` follows the same no-gap principle at handshake time: once FINISH is prepared, Ghost Talk retains the exact FINISH carrier and its original first-message bootstrap state until the responder's **signed bootstrap acknowledgement** proves that FINISH was observed and the responder ratchet became active. The embedded message itself is user-visible **Delivered** once the FINISH carrier is accepted by Kaspa; the acknowledgement is a separate session-activation proof, not the ordinary delivery boundary. If the FINISH send itself returns an error or an already-observed `pq_resp` must be reprocessed after that failure, Ghost Talk reuses the exact cached FINISH bytes; it never re-runs `finish_handshake`, re-encrypts the first message, or allocates another KKTP sequence. A successfully submitted FINISH is not timer-rebroadcast. A responder that encounters an older duplicate FINISH does not decrypt it twice; it reissues the signed acknowledgement for the authenticated embedded `message_id`.

### Realtime voice channel

Strict KKTP reassembly is correct for durable chat but is not appropriate for 350 ms live voice windows: intentionally lost or failed realtime media must not block all later application traffic behind a missing ordered sequence. Ghost Talk therefore treats **live call control/media** as a HYDRA-authenticated realtime extension outside the durable KKTP text sequence. These packets use the existing bounded HYDRA carrier with HYDRA's skipped-key receive window plus the voice protocol's own call-local sequence and jitter buffer. They do not consume `KktpSessionBinding.send_seq` / `recv_next_seq` and they do not generate per-window delivery-ACK transactions.

Recorded **voice messages** are different: they are durable chat messages, so they use normal KKTP ordering and the same logical-carrier/exact-ciphertext retry behavior as text, including GHST physical fragmentation when needed.

This separation is a Ghost Talk application profile of KKTP's extensibility model; the strict ordered mailbox remains authoritative for durable direct-chat events.

## GHST physical fragmentation

The reference KKTP syntax describes the logical Kaspa payload. Ghost Talk already has a bounded, restart-safe `GHST` fragment carrier. To preserve that audited carrier and support PQ handshake sizes, Ghost Talk may place one logical KKTP record inside one or more GHST physical transactions:

```text
Kaspa tx payload: GHST(fragment metadata || logical KKTP bytes)
```

Kaspa Portal 1.0.1 keeps compact KSPT at version 1, whose payload-length field permits at most 65,535 bytes per physical transaction. `GHST_HEADER` is 30 bytes, so `GHST_DATA_MAX` is 65,505 bytes. The 80 KiB Ghost Talk ceiling applies to the reassembled logical carrier; most normal 4 KiB/32 KiB HYDRA carriers therefore use one Kaspa transaction, while only carriers that genuinely cross the KSPT-v1 boundary fragment. Short non-steganographic chat messages use HYDRA's authenticated compact envelope to avoid unnecessary fixed-envelope padding before GHST framing.

Security parsing occurs **after complete GHST reassembly**. Fragment count/size limits and packet-ID conflict checks therefore remain a lower transport layer; they do not replace KKTP `sid`, mailbox, sequence, or HYDRA authentication.

For durable direct messages, the encrypted logical record may span multiple GHST transactions. Ghost Talk caches the exact prepared logical ciphertext and its full fragment vector under the stable `message_id`, then serializes those physical submissions. If post-encryption framing itself fails before any fragment can be submitted, Ghost Talk retires the volatile HYDRA/KKTP session before returning the error so a consumed-but-unpublished sequence cannot create a permanent gap. The fragment-count bound remains finite; application data that exceeds it must be chunked by its application protocol before entering this path.

## Leave, archive, and handshake cancellation

Archive is purely local UI/history state. It does not alter the cryptographic session and never unarchives automatically.

Leave is a session action. For an established direct session, Ghost Talk performs the close in this order:

1. identify the exact active KKTP `sid`, A/B role tuple, authenticated HYDRA peer, sender Kaspa route, and recipient Kaspa route;
2. construct a canonical KKTP v2 `session_end` anchor for that exact tuple with `reason = "left"`;
3. sign the canonical close context with the sender's **ML-DSA-65 HYDRA identity**;
4. include that PQ signature in the anchor and sign the resulting canonical anchor with the sender's **Kaspa BIP340 routing key**;
5. publish the `session_end` as a normal address-targeted Kaspa mailbox transaction;
6. locally close/abort HYDRA state, retire the SID, clear wrapper INIT/RESP/FINISH state, and block the historical peer session;
7. require an explicit new Discovery/Response with a new random `sid` before that peer can send again.

The local Leave action remains immediate even if the network send fails, because local history/session control must not be held hostage by network availability. A remote peer is considered cryptographically closed only after it observes and validates the authenticated `session_end`.

If establishment is still provisional and no active KKTP/HYDRA session exists, Ghost Talk cannot truthfully publish an authenticated close for an active session tuple. It instead aborts only that contact's provisional handshake state, retires any local provisional SID, and leaves locally. The explicit pending-handshake abort is necessary because HYDRA `close_session` applies only after an actual session record exists.

## Session end

Ghost Talk implements the reference protocol's signed on-chain close as the following HYDRA-PQ deployment record:

```json
{
  "type": "session_end",
  "version": 2,
  "sid": "<128-bit lowercase hex>",
  "initiator_hydra_id": "<A HYDRA identity fingerprint>",
  "responder_hydra_id": "<B HYDRA identity fingerprint>",
  "sender_hydra_id": "<A or B HYDRA identity fingerprint>",
  "sender_kaspa_address": "<sender stable P2PK route>",
  "recipient_kaspa_address": "<peer mailbox route>",
  "reason": "left",
  "pq_sig_b64": "<ML-DSA-65 signature>",
  "sig": "<Kaspa BIP340 signature>"
}
```

The record is encoded as:

```text
KKTP:ANCHOR:<canonical-json>
```

Authentication is deliberately **dual-layered**:

- `pq_sig_b64` signs the canonical `session_end` security context with both signature fields omitted, under Ghost Talk's HYDRA application-context domain separation. This binds the close to the post-quantum messaging identity.
- `sig` BIP340-signs the canonical `session_end` record with `sig` omitted but with the already-generated `pq_sig_b64` included. This binds the same close to control of the Kaspa routing address.

A receiver MUST verify canonical encoding, BIP340 routing ownership, ML-DSA-65 identity authentication, local destination, A/B participant tuple, sender identity, peer route, and exact `sid` before changing state. An invalid record is discarded.

A valid close for the **currently bound SID** transitions that session to CLOSED: Ghost Talk closes or aborts the volatile HYDRA state, retires the SID, removes prepared handshake/delivery state, records the peer as blocked for the ended session, and exposes the close to the UI. The composer and live-call control for that exact historical thread are disabled. Native durable send also rejects the blocked peer, so UI state cannot bypass the close.

A delayed valid `session_end` for an **older SID** is idempotently ignored once that SID is retired and MUST NOT close a newer conversation with the same person. The UI persists the exact `sessionSid` on each logical chat and applies a remote close only to that matching SID. Starting a fresh chat is the explicit rejoin boundary: it clears the per-peer native block and creates a new random SID; it does not unarchive or reactivate the old conversation. If the process has restarted and no volatile KKTP binding exists, Ghost Talk may still project a valid close to the persisted matching `sessionSid`, but it does not create a peer-global native block without a live SID binding; this prevents a delayed close from poisoning a fresh session that has not installed its new binding yet.

Archive remains independent of `session_end`. An archived thread stays archived until the user explicitly unarchives it; an ended thread stays ended even if it remains visible locally.

## State machine

Ghost Talk maps KKTP states as follows:

```text
INIT
  -> DISCOVERED      valid Discovery/Response consent tuple known
  -> HANDSHAKE       HYDRA PQ INIT/RESP/FINISH in progress
  -> ACTIVE          HYDRA established + mailbox binding active
  -> CLOSED          local Leave, validated session_end, or replacement session
```

A malformed canonical record, identity/role mismatch, mailbox mismatch, invalid HYDRA authentication, or impossible sequence transition fails closed. Out-of-order future sequence numbers are retained for reassembly rather than immediately faulting the session.

## Legacy compatibility

r44 continues to **decode** legacy `GTCR`, `GTCA`, `GTH1`, and `GTM2` records so already-observed local mailbox data does not become unparsable during upgrade. Newly created direct sessions and newly established message channels use KKTP v2. Legacy wire formats are compatibility-only and are not the target protocol for new traffic.


## Realtime SID-bound transport

Durable KKTP text/recorded-voice delivery keeps its strict per-direction message ordering. Realtime signaling and live voice use a separate exact-session carrier so a lost media window cannot consume `KktpSessionBinding.send_seq` / `recv_next_seq` and stall durable chat.

The Kaspa realtime carrier is `GTR1`: it binds sender identity, logical control/message id and the exact active 128-bit KKTP SID outside the HYDRA envelope, then repeats the SID inside authenticated HYDRA plaintext. Native receive rejects retired/wrong SIDs before the UI sees a control packet. This same carrier transports Auto-mode WebRTC offer/answer signaling and is the live-media fallback.

When Auto establishes WebRTC, Ghost Talk calls native `hydra_seal_direct` before sending a data-channel packet and `hydra_open_direct` before decoding it. The direct path is accepted only for the exact active peer + SID binding, so WebRTC carries opaque HYDRA ciphertext and cannot bypass KKTP session identity. Kaspa only skips peer-connection negotiation entirely.
